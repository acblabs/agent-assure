# agent-assure v0.6.2

v0.6.2 adds a self-digested control-efficacy evidence layer over deterministic
mutation campaigns, with explicit threat applicability, bounded gate semantics,
strict verifier-owned policy binding, evidence-packet integration, and an
offline assurance demonstration.

Highlights:

- adds `ControlEfficacyReport/v1` and
  `ThreatApplicabilityManifest/v1` contracts under the v0.6.2 schema surface;
- preserves the exact catalog detector ratio as
  `caught / (caught + survived)`, including explicit undefined
  zero-denominator state, separate non-verdict counts, every invariant-family
  stratum, and all five independence strata;
- records semantic campaign state separately from configurable gate effects,
  including required and critical survivors, required operators not evaluated,
  invalid or error outcomes, unknown applicability, uncovered critical threats,
  and catalog threat references omitted from the authored manifest;
- makes surviving required and critical operators, required operators without
  a verdict-bearing result, and invalid or error outcomes non-bypassable
  blockers in both runtime and JSON Schema;
- adds `controls efficacy`, standalone and packet `ci gate` support, and
  opt-in `ci --format json` output with structural outcomes for pass, review,
  not-evaluated, failure, and invalid artifact handling;
- strengthens strict verification by independently reconstructing
  catalog-derived and manifest-derived report projections from a separately
  trusted controls-mutation YAML and its confined threat manifest;
- binds efficacy-bearing packets to exactly one report digest, one typed
  configuration digest, the exact gate profile, and a freshly re-derived
  decision while keeping control-challenge scope separate from candidate
  evidence closure;
- adds idempotent `init controls-mutation`, read-only
  `doctor controls-mutate`, and an installed-package offline
  `demo assure-the-assurance` workflow covering caught, survived, and rejected
  substitute-detection paths;
- hardens packet, onboarding, cleanup, and CLI path handling, including
  non-wrapping path output and POSIX rollback protection against concurrently
  replaced files; and
- refreshes all audited dependency locks to `cryptography==50.0.0`, resolving
  `PYSEC-2026-3552`, with repository-relative reproducible lock-generator
  headers.

## Upgrade behavior

Current package and persisted-schema metadata advance to v0.6.2. Existing
released schema snapshots remain frozen for replay; the new efficacy and threat
manifest contracts, and the efficacy-bearing packet fields, belong to the
v0.6.2 writer surface.

When efficacy evidence is present, CLI and programmatic gates now default to
strict verification. Strict verification requires `--efficacy-policy` pointing
to a separately trusted controls-mutation YAML whose referenced threat manifest
is also loaded and checked. A missing policy or threat scope for present
efficacy evidence is invalid input. Efficacy presence remains a separate
choice: `--require-efficacy` requires it, `--efficacy-policy` implies that
requirement, and an otherwise optional packet without efficacy evidence records
that verification was not requested rather than claiming a strict pass.

Packet construction requires `--control-efficacy` and `--efficacy-config`
together. It checks the configuration's current threat-manifest snapshot and
requires the embedded report, profile, decision, configuration role, and file
digests to agree before writing the packet.

A bare gate-profile JSON remains advisory-only and requires
`--allow-advisory-efficacy`. Because that envelope carries no independent
selected-operator set or threat manifest, selected operators are expected to
equal required operators; a selected superset is rejected. Use the
controls-mutation YAML form for strict, manifest-bound verification.

Successful human-readable `ci gate` prefixes now distinguish `review` and
`not-evaluated` from `pass`. Those prefixes remain display text. Automation
should use `--format json`, its structural outcome and reason codes, and the
process exit code. `--fail-on-warn` makes review findings blocking, while
`--fail-on-not-evaluated` covers both efficacy semantic state and threat-scope
state.

Only completed, applicable `caught` and `survived` results with a deterministic
evaluator basis enter the exact ratio denominator. Stochastic or human-reviewed
verdicts are rejected until a typed sufficiency artifact is supported.
Invalid-subject, invalid-operator, execution-error, inapplicable, and pending
states remain visible without being silently counted as survivors.

Catalog threat references absent from the authored manifest now remain explicit
unscoped residuals and require review by default. Unknown applicability and
uncovered applicable critical threats also remain structural review findings;
they are not inferred away from a successful campaign result.

Limitations:

- The authored manifest is a governance input. Validation cannot establish that
  its scope or classifications are complete or that the finite catalog
  represents production failures.
- The current built-in `core/v1` operators are first-party post-control
  challenges. Running them does not by itself establish independent challenge
  coverage, third-party validation, or external red-team assurance.
- A caught result means only that the bound deterministic detector responded to
  that exact transformation under the declared configuration. The report is
  not a system-safety percentage, universal-coverage claim, or statistical
  estimate.
- Gating a schema-valid committed report verifies its bindings and policy
  projection; it does not rerun the mutation campaign or attest that the
  recorded execution occurred. Regenerate the campaign and report from pinned,
  reviewed inputs in CI for an efficacy assurance claim.
- Control-challenge scope remains separate from candidate evidence closure. A
  candidate evaluation can pass while a required or critical control challenge
  blocks packet CI.
- The bundled demo exits successfully when its expected narrative is observed,
  including the expected blocking efficacy decision. Use `--strict` when the
  wrapper should return that underlying blocking exit.
- This implementation note does not claim that release provenance has been
  stamped, that a distribution has been published, or that an external party
  has validated the efficacy evidence.
