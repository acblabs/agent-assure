# agent-assure v0.7.0

v0.7.0 is a feature-frozen hardening release candidate. It strengthens
deterministic evaluation, live execution, privacy boundaries, statistical
claims, evidence integrity, and release governance. The exhaustive change list
remains in the changelog; this note identifies the upgrade and trust-boundary
decisions that operators must make before adoption.

## Security and correctness highlights

- privacy detector profile v9 fails closed if redaction expands a bounded
  scalar beyond the scan limit, uses a bounded URL-secret scanner with explicit
  preflights, UTF-8 percent-obfuscation handling, and complete multi-secret
  redaction, and covers Luhn-valid 13--19 digit cards beside non-digit text plus
  expanded credential and metadata-endpoint defenses;
- external-pilot Git revisions, SHA-256 digests, and workflow run IDs no longer
  fail nondeterministically when they contain a Luhn-valid digit run. This is
  not a global detector bypass: a non-serialized probe projects only exact
  contract-owned paths after complete extra-forbidding typed validation and
  the relevant source, digest, receipt, capture, and workflow-URL bindings have
  been proven. Ordinary text and untyped identifier-shaped fields remain fully
  scanned;
- external-pilot bundles now validate the complete environment, control,
  execution, friction, remediation, and consent bytes against the authoritative
  evidence graph, including one consumed non-bundled participant waiver, one
  derived opaque identity, exact command and inventory bindings, later-source
  remediation, and canonical distinct GitHub workflow runs. Capture publication
  is transactional: a late validation failure cannot leave a partial requested
  capture directory;
- live modules import correctly in fresh processes, independent of package
  import order and ambient decimal state;
- one-sided upper limits and persisted p-values serialize conservatively;
  nondegenerate two-sided live rate, comparison, and ICC intervals serialize
  both endpoints outward; binary cluster-incidence endpoints use exact one-sided
  Clopper--Pearson inversion through 1,000 clusters, the exact zero-event
  closed-form boundary above that threshold, and a separately labeled
  conservative one-sided Bernoulli KL-Chernoff inversion for larger nonzero
  samples. The scalable branches use rational logarithm enclosures and work
  bounded independently of cluster count; KL-Chernoff endpoints use a fixed
  rational grid, round outward, and remain explicitly non-exact. Current
  persisted reports rederive count/rate, distribution, bound, difference,
  test, and gate relationships, require randomization p-values to be attainable
  outward-rounded resample projections, and bind compared clusters to their
  arms and analysis method. Evaluation reports bind their source RunSet,
  completion status, protocol, and bounded observation sufficient statistics;
  comparison reports carry both source-evaluation digests as external linkage
  and their declared source statuses while binding protocol and paired-cluster
  sufficient statistics. Resolving both digests against separately trusted evaluation
  reports establishes source consistency, not provider-side truth. Latency and
  cost absolutes remain source-declarative and non-decision-bearing. Endpoint,
  outcome-category, and
  aggregate resampling work limits are checked before expensive kernels run.
  One evaluation-wide plan includes every nondegenerate overall/group rate and
  eligible ICC bootstrap; exact Clopper--Pearson items are batch-preflighted.
  Evaluation and comparison JSON, Markdown, and console reporters re-enter the
  public validation boundary before rendering or creating output paths, so
  unchecked model copies cannot publish forged decisions. Bounded report
  loading reuses one schema-validated model projection rather
  than repeating all persisted statistical derivations.
  The shared ceiling is 4,096,000 primitive sample/sign units (one 1,000-draw
  ICC bootstrap over 4,096 clusters), exact paired permutation is limited to 17
  clusters, and bootstrap/Monte Carlo protocols
  are rejected at authoring time when their planned clusters exceed the budget;
- fixed-decimal fields now require an exact end-of-string match in both runtime
  and generated JSON Schema validation, including strict closed-unit and
  signed-unit domains. Trailing newlines and values such as `1.999999` are
  rejected. Frozen released schemas receive narrowly scoped in-memory pattern
  corrections; their committed bytes are not rewritten. Every emitted pattern
  and patternProperties expression with an unescaped terminal-dollar assertion
  uses an ECMA-compatible absolute-end assertion; parity tests cover LF, CR,
  CRLF, U+2028, and U+2029;
- live adapter temperature schemas now match runtime validation exactly:
  canonical six-decimal values from 0.000000 through 2.000000;
- canonical identity rejects non-string mapping keys, and controls-map loading
  validates and hashes the same bounded byte snapshot;
- control-coverage reports reject unknown or negative state counters,
  duplicate controls, counters that do not exactly match their items, and item
  states or evidence references that contradict their condition evaluations.
  Condition state must agree with whether its mapping path was observed;
  observed conditions require unique evidence identities; rule identities are
  unique; and mapping requirements, rules, controls, ATLAS identifiers, and
  rendered item limitations reject ambiguous duplicates or noncanonical
  order.
  They also replay deterministic report identity, mandatory claim boundaries,
  and MITRE mapping strength. Non-MITRE reports reject mapping strength and
  ATLAS identifiers. MITRE ATLAS 2026.06 reports validate controls, tactics,
  and techniques against an integrity-pinned offline production catalog, and
  current report IDs bind reviewer-visible mapping titles, strengths, ATLAS
  IDs, and limitations. Valid
  historical report IDs retain their published projection, but contradictory
  historical metadata fails semantic replay. Rendered boundaries, totals,
  states, and evidence are derived from condition facts rather than trusted as
  supplied metadata;
- strict CI applies one warning policy consistently to evaluation, comparison,
  and packet gates; exact active waivers can authorize only their matched
  evaluation warnings, while unrelated warnings and raw comparison regressions
  remain blocking;
- waiver identifiers and authority bindings are unique, identity fields reject
  invisible control/format characters, and evaluation metrics distinguish
  warning-bearing cases from clean passes;
- current expectations require at least one verdict-bearing constraint in both
  runtime validation and the exported writer schema; and
- hosted CI uses the explicit Windows Server 2025 runner label.
- first-party provider authority is restricted to HTTPS port 443, and explicit
  OTLP egress now has a per-request monotonic socket watchdog, no cross-request
  connection reuse, and a 65,536-byte decoded response ceiling.

## Upgrade behavior

The package candidate is version 0.7.0 and emits current writer
`schema_version: 0.6.6`. Released schema snapshots through v0.6.5 remain
immutable.

### Required operator migrations

- OpenAI-compatible network runs in CI now require operator-owned
  `--authorized-endpoint-host` and `--authorized-api-key-env` arguments in
  addition to the existing trust and network opt-ins. Repeat each option when
  authorizing multiple exact values. Do not derive either authorization from
  the live config under test.
- Live adapter pricing is authored with
  `cost_per_million_prompt_tokens_usd` and
  `cost_per_million_completion_tokens_usd`. A complete pair of legacy
  `cost_per_1k_*` fields is still read and converted, but legacy and current
  names cannot be mixed. Schema-v0.6.6 usage-pricing snapshots require
  `input_million_tokens_usd` and `output_million_tokens_usd` strings; legacy
  per-token micro-USD rates require a v0.4.3 snapshot.
- Unquoted YAML dates, floating-point forms, and octal-looking numbers now
  remain strings across suites, variants, live configs, and waivers. Canonical
  decimal integers, booleans, and nulls keep their typed meanings. Recompile
  authored YAML and review any changed canonical digest before reuse.
- Waivers may expire no more than 90 days after the evaluation date. When a
  waiver is supplied, `--today` must equal the actual current local or UTC date;
  historical dates are supported only for waiver-free replay.
- A waiver can authorize its exact warning in a no-baseline evaluation, but it
  never authorizes a `new_failure` or `persistent_failure` comparison
  disposition. Baseline-bearing CI therefore cannot ship an accepted
  pre-existing failure under the current contract.
- The v0.7.0 live-comparison wire contract is schema-breaking. Current
  comparison reports require both source-evaluation digests and completion
  statuses, the complete bound protocol, and per-arm integer
  numerator/denominator counts in every paired cluster. Concurrent arm
  denominators must be positive and equal within each cluster; a fixed
  reference uses baseline counts `0/0`. Regenerate unreleased current
  comparison artifacts and goldens. Keep historical released artifacts labeled
  with their original schema version for frozen-schema replay. Current cluster
  differences are rounded once from exact count ratios, and inference uses the
  unrounded ratios so display precision cannot move a sign or margin boundary.
  Source-evaluation digests remain external linkage: operators must resolve
  both against separately trusted evaluation reports to establish source
  consistency. That resolution does not establish provider-side truth, and
  latency or cost absolutes do not affect the comparison gate state.
- Live drift and trajectory `analysis_methods` are now authoritative rather
  than descriptive metadata. Every drift metric must declare
  `descriptive_trend`, and a confirmatory drift plan must contain a
  confirmatory metric. Every trajectory plan must declare observable
  transitions; event-process and burst-window analysis are a paired method;
  sequence invariants control both invariant and history-check output; and a
  confirmatory trajectory plan must declare all four supported methods plus at
  least one confirmatory invariant target. Exploratory plans reject
  confirmatory invariants, and targetless reports cannot receive a valid
  trajectory status. Current live protocols and reports also require their
  nested analysis plans and plan items to carry the current schema version;
  matching legacy trees remain available through compatibility parsing only.
  Regenerate unreleased current live drift and trajectory artifacts. With
  adequate exposure, a zero-count event stream is a valid observed zero rate;
  positive streams below their declared event-count threshold or with missing
  timestamps cannot emit a plain `burst_signal: none`.
- Current drift windows and trajectory roots persist the effective source
  RunSet/evaluation completion and exploratory state. An incomplete or
  exploratory source invalidates confirmatory monitoring; an exploratory plan
  remains explicitly exploratory. Builders and trusted-source verifiers
  revalidate typed inputs before deriving or resolving evidence. Current live
  RunSets require completion status and stop reasons to agree exactly;
  evaluation replay retains budget exclusions visible in its observations; and
  trajectory source verification reconciles every RunSet-derived observation
  field used for identity, timing, operational, outcome, and cost analysis.
  Trajectory roots persist canonical evaluation stop reasons, bind them into
  report identity, and reconcile budget-stop events exactly, so nested budget
  exclusions cannot be removed or lost when the source RunSet itself is marked
  complete. Only `window_index` and authenticated
  `window_start_utc` drift ordering are supported; `release_sequence` and
  `provider_version_window` now fail closed until authenticated keys are
  implemented. Timestamp ordering also requires strictly increasing window
  starts, so tied timestamps cannot silently inherit caller order. Set-like
  reason-code, analysis-method, forbidden-state,
  exclusion-reason, and provider-capture fields require unique canonical order
  in current protocols, preventing equivalent plans from hashing differently.
  Current trajectory paths use a five-value claim-evidence status contract:
  excluded paths are `not_evaluated`, included non-approval paths are
  `not_applicable`, and only included approval paths may be `complete`,
  `incomplete`, or `unobservable`. Observable evaluator evidence and provenance
  failures are `incomplete`; control-ineligible evidence graph fields are
  `unobservable`, carry explicit path and invariant limitations, and cannot
  claim completeness or suppress the governance warning. The claim-evidence
  invariant's evaluated population contains only observable included approvals;
  unobservable included approvals are counted separately, and excluded
  observations contribute to neither population.
  Reviewed exclusions preserve `human_review → [emergency] → excluded`; the
  emergency state is present only when a linked emergency record exists. For
  excluded observations, runtime-failure and malformed-output facts and
  event-process counts derive only from reason codes on failed policy results
  when the source `policy_results` field has a trusted, control-eligible
  origin. Without that provenance, the failure subtype is not asserted.
  Live evaluation, comparison, drift, and trajectory Markdown/JSON reporting
  revalidates current and historical typed inputs before creating output paths,
  so unsafe model copies cannot display or persist forged decision, ordering,
  or validity state.
- Provider-input accounting and each concrete live adapter revalidate the full
  request before adapter-state access or I/O. Cached governing-evidence policy
  text and structured-output bindings must rederive exactly, preventing an
  unchecked model copy from replacing system-role policy or reaching an
  external provider/script. Direct evidence-diff, study, control-coverage,
  compiled-suite, fixture-manifest, dependency-inventory, RunSet, streaming,
  telemetry, usage, stochastic-evidence, and mutation-gate boundaries also
  round-trip and exact-schema validate before trusted derivation, rendering,
  directory creation, telemetry emission, or canonical serialization. Where a
  historical artifact has complete semantic replay, derived stochastic
  artifacts retain that admitted schema version instead of being promoted into
  current evidence.

This candidate intentionally changes security-relevant producer behavior.
RunSets emitted by v0.6.5 bind privacy detector profile v3. The v0.7.0 runtime
emits profile v9 and does not claim that v3 and v9 are equivalent. Do not edit a
stored profile ID or digest. Regenerate current RunSets from their original
suite, fixtures, and source inputs, or keep historical replay pinned to the
v0.6.5 package. Cross-profile comparisons and release claims fail closed.

Current rare-event cluster-incidence output identifies the selected result
method as `clopper_pearson_exact_one_sided`,
`clopper_pearson_zero_event_closed_form`, or
`bernoulli_kl_chernoff_upper_bound_one_sided` and may differ from development
artifacts produced earlier in the v0.7.0 cycle. Regenerate unreleased current
artifacts and goldens; frozen released schemas and artifacts are not rewritten.

The standalone JSON Schemas remain structural interoperability contracts.
Release or assurance consumers must use the reference runtime validator and
gate for cross-field arithmetic, digest, filesystem, temporal, and replay
invariants.

Historical `evaluation-summary`, `evaluation-report`, `comparison-summary`,
`comparison-report`, and `evidence-packet` roots through v0.6.5 are
archival-only. The public validator, typed loaders and packet writer, and CI
gate reject them; the CLI returns a nonzero `archival-only` diagnostic and
never prints plain validity. Their immutable schemas remain available for
direct shape inspection, and compatibility models remain available to explicit
non-assurance migration tooling, but neither path is assurance acceptance.

Pre-v0.6 live protocol, evaluation, comparison, drift, and trajectory schemas
likewise remain immutable archival shape descriptions, but current assurance
validation rejects those roots because JSON Schema cannot authenticate their
arithmetic or decision state. Historical v0.6.0-v0.6.5 drift and trajectory
roots are also archival-only: their wire forms do not bind the complete plans
and exact source artifacts needed to prove that diagnostics or governance
findings were not removed. Regenerate decision-bearing evidence with the
current writer; use frozen schemas or a pinned historical runtime only for
explicitly non-assurance archival study or migration.

v0.6.0-v0.6.5 live protocol records retain compatibility only through the
reference runtime's semantic projection. Frozen-schema acceptance alone is not
sufficient: the runtime revalidates their cross-field sample-design arithmetic
and rejects contradictory plans.

### CI, packaging, and support qualification

The v0.7.0 composite action has a supported strict assurance route: provide
both `control-efficacy-report` and a separately trusted `efficacy-policy`. The
action binds the current evaluation summary into an efficacy-bearing packet and
strictly re-verifies that packet. The policy must come from verifier-controlled
workflow state; a policy changed by the candidate is not independent authority.
Evaluation-only jobs must explicitly choose
`allow-missing-efficacy-for-migration: "true"`, and that result remains labeled
non-assurance. The two modes are mutually exclusive and incomplete input pairs
fail closed. Action output paths must be strict descendants of
`GITHUB_WORKSPACE` or `RUNNER_TEMP`; traversal, filesystem roots, and
linked/reparse-point ancestors are rejected before and after directory
creation. The strict efficacy-bearing path is confined to `GITHUB_WORKSPACE`
because its packet is verified against that artifact root.
CI now invokes the local composite action in two separate jobs on actual Ubuntu
runners. The explicitly labeled non-assurance fixture profile remains isolated.
The strict job creates a deterministic passing control-efficacy campaign and
policy fixture, supplies both strict inputs to the action, disables artifact
uploads, requires the packet, graph, manifest, reports, and deterministic inputs
to be present and nonempty, and independently repeats the strict efficacy gate.
This is implementation-path qualification, not independent production evidence.

Release and TestPyPI publication now require exact-source-SHA jobs that audit
all five current hashed lockfiles on Ubuntu 24.04 and Windows Server 2025 under
Python 3.11 and 3.14 and re-run the bounded credential-material scan against
the exact uploaded wheel and sdist. Every matrix cell is a fail-closed
publication dependency. The matrix evaluates applicable environment markers
and advisories; it does not claim that the Python 3.11/Linux-specific optional
adapter locks install on every matrix target. The routine security workflow
uses the same audit matrix and also builds and scans the release payload. These
scans complement review and platform secret protection; they are not a
guarantee that every possible secret representation can be detected. The
recovery path audits all four pinned historical lockfiles on Ubuntu 24.04 and
Windows Server 2025 under Python 3.11 and 3.14 before verification. It also
reconstructs the frozen v0.6.0 SBOM from the manifest's environment inventory
and the exact wheel/sdist bytes; publication still requires the later signature
and byte-identity verification. Recovered evidence therefore cannot inherit a
stale, marker-incomplete dependency audit or a self-consistent truncated SBOM.

The standard production tag path now fails closed unless GitHub registers SLSA
v1 provenance for the exact 22 assets that passed fresh-job signature and
binding verification. The provenance-registration job is tag-only, protected by the
`signing` environment, consumes only an immutable 22-line checksum artifact
emitted by the fresh verifier, and contains no checkout, shell, dependency
installation, or project-code execution. The action is pinned to the full
`actions/attest` v4.2.2 commit SHA. This is workflow-level provenance, not an
independent-builder or SLSA Build Level 3 claim. TestPyPI candidates are
intentionally not granted provenance-registration or additional OIDC authority.

All five current release-tested dependency locks use `urllib3` 2.8.0, resolving
`PYSEC-2026-4175`, `PYSEC-2026-4176`, and `PYSEC-2026-4177` before publication.

A separate hash-locked lower-bound profile now runs the complete suite on
Python 3.11 and 3.14 in ordinary CI and again against the exact release or
TestPyPI candidate SHA as a mandatory publication dependency. Its direct
constraints match the declared runtime floors; the qualified Typer floor is
0.19.0 because that is the first release that can construct the CLI's
`typing.Literal` parameters, and the qualified PyYAML floor is 6.0.3 for Python
3.14 installation support.

The routine security workflow now scans the complete Git history with Gitleaks
v8.30.1 pinned by container digest. Suppressions are limited to exact known
synthetic test tokens, and findings are redacted in CI output. A runtime canary
introduced only in a temporary repository's merge result must be detected
before the repository result is trusted. First-parent merge-result diffs,
independent non-empty revision enumeration, and an exact match between parsed
positive scan statistics and a unique Git patch-unit enumeration prevent a
silent or partial history scan from reporting success. The security workflow
has no `main` push path exclusion, so
pilot-input-only commits cannot skip the complete-history scan.

Historical artifacts with a complete public semantic replay now report
`frozen-jsonschema+semantic-replay`, so validation output cannot be mistaken
for a shape-only frozen-schema check.

Release-bundle construction reopens the exact persisted SBOM bytes before
manifest inclusion and reconstructs the complete expected document from the
trusted environment snapshot, exact distribution allowlist, verified lock
graph/hashes, and project metadata. Canonical package and file identities,
purls, components, dependency edges, composition, serial, and exact local bytes
must match, so in-memory generation alone cannot authorize incomplete or
inconsistent persisted SBOM evidence. The standalone SBOM CLI validates local
self-consistency but cannot prove environment or file-set completeness without
those separately trusted release inputs.

Committed external-pilot inputs are now read through a bounded Git object
verifier that rehashes the named commit, each traversed tree, and the final blob
before accepting bytes. Canonical object types, sizes, path modes, traversal
limits, and subprocess deadlines are enforced; a corrupt or substituted loose
object is rejected even if Git prints it for the requested object ID.

Machine-readable CI decisions now include `envelope_version: "1.0.0"`.
Persisted evaluation reports reject duplicate waiver dispositions and any
disposition/replay-waiver mismatch. Live reports render nested invariant,
rare-bound, and correlation limitations beside their estimates. The wheel is
marked with `py.typed`; the source distribution includes the reviewed security
and governance documents; and `.agent-assure-*.lock` coordination files are
ignored by Git without changing their intentional on-disk lifetime.

The external-pilot quickstart no longer asks a second person to approve its
deliberately non-matching waiver input. The participant supplies a distinct
schema-only reviewer label; documentation makes explicit that the label grants
no authority and is not a human approval.

The release-qualified platform matrix is the full suite on Ubuntu 24.04 with
Python 3.11, 3.12, 3.13, and 3.14, plus the native containment subset on Windows
Server 2025 with Python 3.11 and 3.14. macOS is not CI-qualified. The five
hashed `requirements*.lock` files are the current release-tested dependency
sets; the broader `pyproject.toml` ranges state compatibility intent rather
than complete combinatorial qualification.

## Release authorization

This file does not authorize publication. The standard publication workflow
still requires the separately staged verifier-owned control-efficacy packet and
policy, the frozen confirmatory benchmark and approval evidence, external-pilot
evidence and independent review, engineering release checks, and exact clean
candidate-SHA replay. Missing empirical or efficacy evidence fails closed.

The repository-local security-maintenance publication bypass is disabled in
this candidate. When a supported deployment remains exposed while a correction
is blocked, the [security correction containment and risk-acceptance
runbook](../security_release_containment.md) requires verified compensating
controls, tested monitoring, a named accountable owner, a distinct authorized
security approver, customer and advisory coordination, a severity-bounded
expiry, reevaluation, escalation, and an auditable private record. That record
may govern only temporary operation of the named deployment; it cannot
authorize a merge, tag, signature, GitHub Release, TestPyPI or PyPI publication,
or a release-gate exception.

## Verification boundary

Population-inference flags are conditional on authored protocol assumptions and
artifact consistency. They do not independently establish exchangeability,
causal identification, external validity, provider quality, regulatory
compliance, or production safety. Live reports label observation-level event
rates separately from independent-cluster incidence bounds.
